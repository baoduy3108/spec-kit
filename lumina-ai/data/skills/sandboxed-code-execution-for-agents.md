# Sandboxed Code Execution for Agents

The moment an AI agent can **run commands** — a coding agent, a code interpreter, a "run this snippet" feature — you are executing code that is **untrusted by construction**: it was generated by an LLM (which can be wrong or manipulated via prompt injection) to act on a task from a user. Running that on your normal server is a critical vulnerability. **Sandboxing** — strong isolation between the executed code and everything else — is what makes agent execution safe, and it's the infrastructure most of the difficulty lives in (see coding-agent-architecture, agent-safety-and-action-guardrails, ssrf-and-url-fetch-safety).

## The Threat Model

Assume the code the agent runs is **adversarial**:
- It might `rm -rf`, read secrets/env vars, exfiltrate data, or crypto-mine.
- **Prompt injection** in a file/webpage the agent reads can *redirect* it to run malicious commands.
- Even honest agents make destructive mistakes (delete the wrong files, spawn runaway processes).
So the sandbox must contain both **malice** and **accidents**, giving the code only what the task genuinely needs.

## The Isolation Layers

- **Container / microVM** — run the agent's shell inside a **Docker container** or a lightweight **microVM** (Firecracker/gVisor), not on the host. MicroVMs/gVisor give stronger kernel isolation than plain containers for truly untrusted code.
- **Filesystem isolation** — the agent sees only its **workspace** (the repo), not the host filesystem, other tenants, or secrets. Mount narrowly, read-only where possible.
- **Network egress control** — restrict outbound traffic: block the cloud **metadata endpoint** (169.254.169.254 — see ssrf), internal ranges, and unneeded hosts; allowlist what the task needs. Prevents data exfiltration and SSRF-style pivots.
- **Resource limits** — cap CPU, memory, disk, process count, and **wall-clock time** so runaway/mining code can't take down the box (cgroups/ulimits).
- **No ambient credentials** — don't run the sandbox with cloud keys or DB access the agent could steal; inject only scoped, task-specific secrets if truly required.
- **Ephemeral, per-task environments** — spin up a **fresh** sandbox per task/session and **destroy** it after, so nothing persists or leaks between users.

## Why a Chat App Can't "Just Run Code" Safely

Adding "execute the code the AI wrote" to a normal web app without this isolation means arbitrary remote code execution on your server — game over. Safe execution requires the whole sandbox stack (container/microVM orchestration, isolation, egress control, lifecycle). That's exactly why "let the chatbot run code" is a major engineering undertaking, not a feature toggle — and why systems that do it (OpenHands, code interpreters) invest heavily here.

## Design Guidance (for understanding/using)

- **Never run agent/LLM-generated code on the host** — always inside a container/microVM with least privilege.
- **Isolate filesystem + network** — workspace-only mounts, egress allowlist, block metadata/internal IPs.
- **Cap resources and time** — CPU/mem/disk/process/wall-clock limits to contain runaways.
- **Strip credentials** — no ambient cloud/DB keys reachable from the sandbox; scope any needed secret tightly.
- **Make sandboxes ephemeral** — fresh per task, destroyed after; assume each run is compromised.

## Pitfalls (in understanding/using)

- Treating "run code" as a simple feature → it's **arbitrary RCE** without a sandbox.
- Using a **plain container** for fully untrusted code and assuming kernel-level safety → consider microVM/gVisor for strong isolation.
- Leaving **egress open** → data exfiltration and metadata-credential theft (SSRF).
- Running the sandbox with **cloud/DB credentials** in reach → the agent can steal them.
- Reusing a **long-lived** sandbox across users → cross-contamination and persistence of malicious changes.
